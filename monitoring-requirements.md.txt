# ContentSphere Monitoring Project
## Task 1 — Monitoring Requirements

### 1. Project Objective
The objective is to monitor the availability, performance, and reliability of the ContentSphere platform hosted on AWS. The solution will collect infrastructure metrics, centralize logs, display dashboards, and generate alerts for important operational problems.

### 2. Application and Infrastructure Components
- Amazon EC2 running Ubuntu Linux
- ContentSphere application and its application logs
- Node Exporter for Linux host metrics
- Prometheus for metrics collection and storage
- Grafana for monitoring dashboards
- Amazon CloudWatch for AWS infrastructure metrics
- Amazon SNS for email notifications
- Fluent Bit for log collection and forwarding
- Elasticsearch for log storage and indexing
- Kibana for log search and visualization

### 3. Monitoring Requirements
- Monitor CPU utilization and server availability.
- Monitor memory usage and available memory.
- Monitor root filesystem utilization.
- Monitor network traffic.
- Monitor application errors and response latency where instrumentation is available.
- Collect application, web-server, and operating-system logs.
- Detect unavailable monitoring targets.
- Generate alerts for sustained high CPU utilization and EC2 status-check failures.
- Verify that collected logs can be searched and analyzed.

### 4. Initial KPI Matrix

| KPI | Warning | Critical | Monitoring Source |
|---|---|---|---|
| CPU utilization | Above 70% | Above 85% | Prometheus / CloudWatch |
| Memory utilization | Above 75% | Above 90% | Node Exporter |
| Root filesystem utilization | Above 75% | Above 90% | Node Exporter |
| Application HTTP 5xx errors | Increasing error rate | Sustained error rate | Application instrumentation / logs |
| Monitoring target | Intermittent failures | Target remains down | Prometheus |
| Log ingestion | Delayed events | No expected events | Fluent Bit / Elasticsearch |
| EC2 status checks | Check failure detected | Instance remains unhealthy | CloudWatch |

These are initial lab thresholds and must be adjusted according to observed workload and operational requirements.

### 5. Monitoring and Logging Architecture
Metrics flow:
ContentSphere EC2 → Node Exporter → Prometheus → Grafana.

AWS monitoring flow:
EC2 and EBS → CloudWatch Metrics → CloudWatch Dashboard and Alarms → SNS Notifications.

Logging flow:
Application and System Logs → Fluent Bit → Elasticsearch → Kibana.

### 6. Incident Investigation
When an alert occurs, the operator will check the relevant Grafana panels, review CloudWatch metrics, search Kibana logs around the incident timestamp, identify the likely cause, apply a corrective action, and verify that the issue has been resolved.

### 7. Security and Cost Control
- Restrict monitoring ports using AWS security groups.
- Avoid exposing Elasticsearch and Kibana directly to the public internet.
- Do not commit passwords, access keys, or tokens to GitHub.
- Use suitable access controls and encrypted connections.
- Review AWS resource usage and delete or stop unnecessary lab resources.
- Select resource sizes according to the workload and available budget.

- CloudWatch dashboard, alarms, and SNS notification evidence

- Kibana log analysis dashboard

- README.md and monitoring-project-report.txt
